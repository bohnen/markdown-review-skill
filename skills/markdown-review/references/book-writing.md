# 技術書原稿の規約（Claude 向け短縮版）

正は `book-style-guide.md`（規約）と `book-writing.md` の後半（レビュー手順）。判断に迷ったらそちらを読む。優先順位は「事実 > 規約 > 好み」で、規約に合わせる書き換えで事実・主張・固有名詞・数値を変えない。コードブロックの中は変更しない。

## 文体

- 地の文は `ですます`。箇条書きの項目と表のセルは常体か体言止めで、行末に句点を打たない。用語と説明の区切りは全角「：」
- 本は「本書」、書き手は「筆者たち」、読者は「読者の皆さん」「皆さん」。`あなた`、`私`、`みなさん` は使わない。
- 「〜してみましょう」は誘い、「〜してください」は手順の指示。「〜しよう」は見出しだけ。
- `思います` は使わない。「〜たり」は対で使う。重言（`まず最初に`、`各〜ごと`）を使わない。

## 構成

- 章ファイルは frontmatter（`author: 名前 <メール>`）→ `# 第N章 タイトル` → `本章では〜します` → 前章との接続 → 読み飛ばし許可、の順で始める。
- 節見出しの番号形式（例：`## Chapter N-M: [タグ] タイトル`。半角コロン、タグは番号の後ろ、半角ブラケット）を 1 つ決めて全章で使う。深さは h4 まで。
- 手を動かす節には書籍のコンセプトに合う動詞をタグにする（`[準備]` `[実行]` `[復旧]`、`[実践]` `[検証]` など）。
- 章末はまとめの節にし、見出し名を全章で揃える。やったこと → 要点の箇条書き → 次章への 1 文、の順で書く。
- コラムは `### コラム：タイトル` で始める。本文から「興味のある読者はコラムで〜」と送り出す。

## コードとコマンド

- info string は `言語 ラベル`。読者が打つのは ```` ```bash コマンド ````、結果は ```` ```bash 実行結果 ````、設定ファイルは ```` ```yaml ファイル名 ````。言語は bash / sql / text / yaml / json / ini / hcl。
- コピーして貼り付けるブロックにプロンプトを付けない。結果を見せるブロックは `$`（後ろに半角スペース）（シェル）と `mysql>`（後ろに半角スペース）（SQL）を付けて 1 ブロックにする。
- 長い出力は `..省略..` で省き、直後に何を省いたかとどこを見るかを書く。
- 環境で値が変わる出力には「何が違ってよいか」と「何が一致すべきか」をセットで書く。
- エラーメッセージは隠さず載せ、直後に 1〜2 文で意味を説明する。
- インラインコードはコマンド・オプション・テーブル名・カラム名・パス・設定値・SQL キーワード（「`SELECT`文」）。製品名（TiDB、MySQL）は地の文で公式の大文字小文字。
- 紙の書籍では Mermaid を使わず、図は PNG を `img/` に置く。ブログやオンライン文書では Mermaid を使ってよい。

## 図表

- 画像は `![日本語キャプション](img/ファイル名.png)`。パスは章ディレクトリ相対。図番号は付けない。本文で言及してから置く。
- 比較表は 1 列目を太字。リファレンス表は「名前／指定例（インラインコード）／説明（常体）」の 3 列。

## 表記

- 括弧は全角「（）」。英数字と日本語の間にスペースを入れない。ダッシュと並列の中黒を地の文で使わない。プレースホルダーは `<説明>`。
- 長音は -er/-or/-ar で長音付き（サーバー、ユーザー、クラスター、マスター、リーダー、パラメーター）。慣用で長音なし（アーキテクチャ、プライマリ、リカバリ、レイテンシ）。「インターフェイス」は「フェイス」と書く。
- ひらく：すべて／さまざま／たとえば／さらに／したがって／など／とおり／とき／ため／ほか／わかる／うえで／ごとに。閉じる：先ほど／行う／表す。「その他」は漢字のまま。`アプリ` は「アプリケーション」と書く。
- 初出用語は「日本語（English）」または「略語（Full Spelling）」で併記し、区切りは全角「：」。初出の定義語は太字、以後は「」。
- 太字は用語の初出と箇条書きの小見出しだけ。注意書きは専用記法を使わず地の文（「注意点として」「〜に注意してください」）。
- 補足・出典・前方参照は脚注 `[^名前]`。定義は参照段落の直後に置く。

## 説明の展開

- 操作は「概念 → 実践 → 確認 → 意味づけ → 本題への接続」の順。障害を起こす章は「準備（復元手段）→ 壊す → エラー → 解説 → 直す」。
- 同じ操作の説明は序盤ほど丁寧に、後半ほど簡潔に（序盤「取得（SELECT）」、後半「SELECT」）。
- 割愛は「割愛する旨 + 理由 + 代わりの行き先（脚注 URL・書籍）」の 3 点セット。
- 構成の数（台数など）には根拠を書く。サンプルデータは 1 セットを全章で使い回す。
- 比喩は既知の概念（クラスとインスタンス、表計算のシート）に着地させる。指す内容が一意でない比喩は使わない。

## 運用

- ファイル構成は対象プラットフォームの規約に従う。書籍に含めないメモや下書きは、ビルド対象から外れる命名（`_` 始まりなど）で区別する。
- textlint の制御コメントは原則使わない。必要なら `<!-- textlint-disable ルール名 -->`〜`<!-- textlint-enable -->` で最小範囲。
- 編集者の表記指示は 1 か所に記録し、繰り返し出るものから prh ルールへ昇格させる。

## レビューするとき

- 順番は「機械 lint → 表記 → 構成 → 内容 → 文章規範」。段 1 を済ませてから次へ。
- prh、句点欠落、接続詞重複、漢字連続、冗長表現はその場で直す。一文の長さ、読点の数、弱い表現、文体混在は提案に回す。箇条書き・表・キャプション・脚注 URL の句点欠落は誤検知。
- 語を削って lint を通さない。件数はルール ID ごとに「修正済／提案へ／誤検知」に仕分けて報告する。
- 指摘は「箇所／規約（book-style-guide.md の節番号）／修正案」の 3 点で書く。

## 技術書原稿レビューガイド

`book-style-guide.md` の規約に照らして、章単位の Markdown 原稿をレビューする手順とチェックリストです。人がレビューするときも、Claude（markdown-review プラグインの `book` 種別）がレビューするときも、同じ順番で見ます。

### 1. レビューの流れ

| 段 | 見るもの | 道具 |
| --- | --- | --- |
| 1. 機械 lint | Markdown 構造、日本語の機械的な問題、表記ゆれ | markdownlint、textlint（`preset-ja-technical-writing` + prh） |
| 2. 表記 | prh が拾えない記号・スペース・呼称 | 目視、`grep` |
| 3. 構成 | 見出し形式、タグ、まとめ、コラム、frontmatter | チェックリスト（3 章） |
| 4. 内容 | 展開パターン、エラーの見せ方、環境差の注記、割愛の行き先、グラデーション | チェックリスト（3 章） |
| 5. 文章規範 | 段落構成、論証、冗長、演出 | 一般の日本語の技術文書の規範（markdown-review の `japanese-tech-writing.md`） |

段 1 を通してから段 2 以降に進みます。段 1 の指摘が多い原稿で構成の議論をしても、直した後に位置がずれます。

### 2. textlint ルールの扱い

「その場で直す」「提案に回す」「誤検知として除外する」を取り違えないことが、機械 lint を役立てる要点です。

| 扱い | ルール | 補足 |
| --- | --- | --- |
| その場で直す | `prh` 全般 | 事実・固有名詞・コードには触れない。製品名の大文字小文字はプロジェクト固有辞書に従う |
| その場で直す | `ja-no-mixed-period`（句点欠落） | 例外は下記「誤検知」を参照 |
| その場で直す | `no-doubled-conjunction`（接続詞の重複） | |
| その場で直す | `max-kanji-continuous-len`（漢字の連続） | 語を削らず、助詞や読点で区切る |
| その場で直す | `ja-no-redundant-expression`（冗長表現） | `することができます` → `できます` |
| 直せれば直す | `no-doubled-joshi`（助詞の重複） | 意味を保つ語順変更や言い換えで直す。無理なら提案に回す |
| 提案に回す | `sentence-length`（一文の長さ） | 文の分割は主張に触れるため、案を示して著者が決める |
| 提案に回す | `max-ten`（読点の数） | 同上 |
| 提案に回す | `ja-no-weak-phrase`（弱い表現） | `思います` は原則直す。推量・読者の疑念・仮定を表す `かもしれない` は残す |
| 提案に回す | `no-mix-dearu-desumasu`（文体の混在） | 箇条書きと表の常体は規約どおり。地の文の常体だけ指摘する |
| 誤検知 | `ja-no-mixed-period` が次の行に当たる場合 | 箇条書きの項目、表のセル、図のキャプション、「〜：」で終わる導入句、脚注の URL 行 |
| 誤検知 | `max-ten` が参考文献の著者名列挙に当たる場合 | |
| 対象外 | コードブロックの中 | 表記規約の対象外。変更しない |

件数を報告するときは、「未修正 N 件」と丸めず、ルール ID ごとに「修正済／提案へ／誤検知」に仕分けます。

### 3. チェックリスト

章ごとに確認します。prh が検出する項目（長音、ひらく漢字、重言）は省いています。

#### 3-1. 表記（目視）

- [ ] 日本語文中の括弧が全角「（）」になっている
- [ ] 英数字と日本語の間にスペースが入っていない（出版社指示に従う）
- [ ] `思います` を使っていない
- [ ] 「〜たり」が対で使われている
- [ ] 読者の呼び方が「読者の皆さん」「皆さん」で統一されている
- [ ] 書き手が「筆者たち」、本が「本書」で統一されている
- [ ] 初出の用語が「日本語（English）」で併記され、区切りが全角「：」になっている
- [ ] 太字が用語の初出と箇条書きの小見出しに限られている
- [ ] 製品名がバッククォートなしで、公式の大文字小文字で書かれている
- [ ] プレースホルダーが山括弧 `<説明>` で統一されている
- [ ] ダッシュや並列の中黒を地の文で使っていない

#### 3-2. 構成

- [ ] frontmatter に `author:` がある。表記がほかの章と揃っている
- [ ] 章の冒頭が `本章では〜します` で始まり、前章との接続と読み飛ばし許可が書かれている
- [ ] 節見出しの番号形式・コロン・タグ位置がほかの章と揃っている
- [ ] 見出しの深さが h4 以内
- [ ] 見出しが内容を特定する句になっている（「まとめ」「例に戻す」だけになっていない）
- [ ] 手を動かす節にタグ（`[準備]` `[実行]` `[復旧]` など）が付いている
- [ ] 章末のまとめの見出し名がほかの章と揃い、「やったこと → 要点の箇条書き → 次章への 1 文」の形になっている
- [ ] コラムが `### コラム：タイトル` で始まっている
- [ ] 本文からコラムへの送り出し文がある
- [ ] テンプレートの HTML コメントが残っていない
- [ ] 参考文献やメモが、書籍に含めないファイルへ分けられている

#### 3-3. コードと図

- [ ] コードブロックに言語指定がある
- [ ] 読者が打つブロックは ```` ```bash コマンド ````、結果は ```` ```bash 実行結果 ```` のラベルが付いている
- [ ] コピーして貼り付けるブロックにプロンプトがない。結果を見せるブロックには `$`（後ろに半角スペース） か `mysql>`（後ろに半角スペース） がある
- [ ] 省略が `..省略..` で統一され、直後に「何を省いたか」「どこを見るか」が書かれている
- [ ] 環境で値が変わる出力に「何が違ってよいか」「何が一致すべきか」が書かれている
- [ ] エラーメッセージが載っていて、直後に意味の説明がある
- [ ] 画像が `![日本語キャプション](img/ファイル名.png)` で、本文で言及してから置かれている
- [ ] 画像パスが章ディレクトリ相対の `img/` になっている
- [ ] 表の 1 列目（比較表）が太字、リファレンス表の指定例がインラインコードになっている
- [ ] 紙の書籍の場合、Mermaid を使っていない

#### 3-4. 内容

- [ ] 操作の説明が「概念 → 実践 → 確認 → 意味づけ → 本題への接続」の順になっている
- [ ] 障害を起こす実験の前に、復元手段（バックアップ、再作成コマンド）が示されている
- [ ] 同じ操作の説明が、後半へ進むにつれて簡潔になっている（グラデーション）
- [ ] 割愛に「理由」と「代わりの行き先」が添えられている
- [ ] 構成の数（台数、レプリカ数）に根拠が書かれている
- [ ] 脚注の定義が参照段落の直後に置かれ、参照されない脚注がない
- [ ] 前方参照（「後の章で説明します」）の回収先が実在する
- [ ] サンプルデータがほかの章と同じものになっている

### 4. 指摘の書き方

- 指摘は「箇所」「該当する規約」「修正案」の 3 点で書く。規約は `book-style-guide.md` の節番号で示す
- 事実、主張、固有名詞、数値は書き換えない。表記と構成の指摘にとどめ、内容の疑問は質問として書く
- 推量や読者の疑念として書かれた文（`かもしれない`、`だろう`）を、機械的に断定へ変えない
- 語を削って lint を通さない。漢字の連続や助詞の重複は、助詞や語順で解消する
- 修正で語義が変わりうる箇所は、その旨を報告に明記する

### 5. 報告の形式

```text
対象: Part2/chapter5/chapter5.md（書籍原稿）
機械 lint:
  prh                      12 件 → 修正済 12
  sentence-length           4 件 → 提案 4
  ja-no-mixed-period        3 件 → 誤検知 3（箇条書き）
表記・構成: 見出し 2 件（5-2 の形式ゆれ）、コラム閉じ 1 件
内容: 環境差の注記なし 1 件（`tiup playground display` の出力）
提案: （文の分割案、修正案）
```
