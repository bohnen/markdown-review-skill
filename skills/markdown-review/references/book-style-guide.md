# 技術書原稿スタイルガイド

ハンズオン形式の日本語技術書（章単位の Markdown 原稿）を書くときの規約です。

- 表記ゆれの多くは prh 辞書（`config/prh/`）が機械的に検出する。このガイドはその背景と、機械では拾えない構成・語り口のルールを扱う
- レビューの手順とチェックリストは `book-writing.md` の後半、Claude 向けの短縮版は `book-writing.md` の前半にある
- 優先順位は「事実 > 規約 > 好み」。規約に合わせる書き換えで事実や主張を変えない

## 1. 文体

### 1-1. 地の文は「ですます」、箇条書きと表は常体

地の文は語りかける調子の「ですます」で書きます。硬い解説調にしません。

```text
突然ですが、データベースってなんでしょうか。
本章では、前章までに説明した各コンポーネントの数を増やして、スケーラビリティと耐障害性を確認します。
```

箇条書きの項目と、表の説明セルは常体（である・する）か体言止めにし、行末に句点を打ちません。用語と説明の区切りは全角の「：」です。

```markdown
- コンピューティングノードが全部停止する
- **Atomic（原子性）**：トランザクションの操作がすべて成功するか、すべて失敗するかのどちらかになる
```

### 1-2. 一人称と読者の呼び方

| 対象 | 使う | 使わない |
| --- | --- | --- |
| 本そのもの | 本書 | この本、当書 |
| 書き手（共著） | 筆者たち | 私、我々、`筆者達` |
| 読者 | 読者の皆さん、皆さん、読者の方 | あなた、`みなさん` |

「読者の方は〜しても構いません」という読み飛ばし許可を、章や節の冒頭に置いてよいです。

```text
すでに NewSQL について知っている読者の方は第2章に進んでも問題ありません。
```

### 1-3. 誘導表現の使い分け

| 表現 | 用途 | 例 |
| --- | --- | --- |
| 〜してみましょう | 読者を次の操作へ誘う（段落の締め） | 実際に起動して、コンポーネントを停止させてみましょう |
| 〜してください | 手順の指示 | ターミナルを 1 つ起動して、次のコマンドを実行してください |
| 〜ではないでしょうか | 読者の経験に同意を求める | 使うデータベースの数は片手で数えるくらいではないでしょうか |
| 〜しよう | 見出しだけ | Chapter 2-2: TiDB クラスターをつくろう |

1 段落で「〜してみましょう。〜してください。」と続くのが典型です。

### 1-4. 使わない表現

- `思います` は使わない。幼く見えるので、根拠を示して言い切るか、`〜と考えています` や `〜と見ています` に変える
- 「〜たり」の単独使用。「〜したり、〜したり」と必ず対で使う
- 重言。`まず最初に` は「まずは」、`各ノードごと` は「ノードごと」、`あとから追加する` は「追加する」
- `〜することができます` は `〜できます` にする。二重敬語は使わない

## 2. 章と節の構造

### 2-1. 章ファイルの冒頭

frontmatter に担当者を書き、章見出し、導入段落、読み飛ばし許可、本章のゴールの順で始めます。

```markdown
---
author: 名前 <メールアドレス>
---

# 第3章 NewSQL クラスターへ接続しよう

本章では、第2章で起動した TiDB クラスターに接続して、簡単な SQL を実行します。
MySQL の SQL 文法に慣れている方は、読み飛ばしていただいて構いません。
```

導入段落は「本章では〜します。」で始め、前章との接続を 1 文添えます。

### 2-2. 見出しの形式

- 節見出しの番号形式を 1 つ決めて全章で使う（例：`## Chapter N-M: [タグ] タイトル`。番号のあとは半角コロンと半角スペース、タグは番号の後ろに半角ブラケット）
- 深さは h4（`####`）まで。h5 以下が要るときは節を分ける
- 章をまたいで同じ形式を使う。`N-M` と `N.M`、半角コロンと全角コロンを混ぜない
- 見出しは内容を特定する句にする。「例に戻す」のような手順だけの見出しや、「まとめ」だけの見出しにしない

### 2-3. ハンズオン節のタグ

書名の動詞を、手を動かす節のマーカーとして見出しに入れます。読者は目次で「手を動かす節」を見分けられ、組版ではアイコンを割り当てられます。

| タグ | 意味 |
| --- | --- |
| [準備] | 環境やデータを構築する |
| [実行] | 意図的に停止・破壊して挙動を見る |
| [復旧] | 復旧・バックアップ・リストアを行う |

書籍のコンセプトに合う動詞（`[実践]`、`[検証]`、`[演習]` など）へ置き換えて構いません。

### 2-4. 章末のまとめ

章の最後の節はまとめにし、見出し名（「ここまでのまとめ」など）を全章で揃えます。次の 3 段で書きます。

1. 本章で何をしたか（1〜2 文）
2. 要点の箇条書き
3. 次章への 1 文（「次章では、この動作の背景となるアーキテクチャを見ていきましょう。」）

次章への 1 文は省略しません。

### 2-5. コラム

上級者向けの分岐や本筋から外れる話題は、コラムに逃がします。

```markdown
### コラム：1台のストレージノードからクラスターを復元する

（本文）
```

- 見出しは「コラム：」のあとに内容を特定するタイトルを書く。「補足」「基礎」のような種別名だけにしない
- 本文からは「興味のある読者はコラムの手順で挑戦してみてください。」と送り出す。本筋は最短ルートを示す

## 3. コードとコマンド

### 3-1. コードブロックの言語とラベル

info string の 1 番目に言語、2 番目に日本語のラベルかファイル名を書きます。

| 用途 | 書き方 |
| --- | --- |
| 読者が打つコマンド | ```` ```bash コマンド ```` |
| その実行結果 | ```` ```bash 実行結果 ```` |
| SQL | ```` ```sql ```` |
| 設定ファイル | ```` ```yaml topology.yml ```` |
| 構成やログなどの整形テキスト | ```` ```text ディレクトリ構成 ```` |

言語は `bash`、`sql`、`text`、`yaml`、`json`、`ini`、`hcl` を使います。ラベルは「コマンド」「実行結果」の 2 語に統一し、「出力結果」は使いません。

### 3-2. プロンプトの有無

- 読者がコピーして貼り付けるブロックには、プロンプトを付けない
- 実行結果を見せるブロックには、シェルは `$`（後ろに半角スペース）、SQL クライアントは `mysql>`（後ろに半角スペース） のプロンプトを付けてコマンドと出力を 1 ブロックに入れる

```text
$ tiup playground display

Pid    Role     Uptime
---    ----     ------
81119  pd       42.09704632s
```

### 3-3. 出力の省略と環境差

- 長い出力は `..省略..` で省き、直後の本文で「何を省いたか」「どこを見ればよいか」を書く
- 環境によって値が変わる出力には、「何が違ってよいか」と「何が一致すべきか」をセットで書く

```text
Pid や Uptime の値は環境によって異なりますが、出力される行数は上記と同じになるはずです。
```

### 3-4. エラーは隠さない

うまくいかない出力は主役として載せ、直後にエラーコードの意味を 1〜2 文で説明します。読者がもっとも孤立する瞬間を本文に取り込みます。

```text
ERROR 9005 (HY000): Region is unavailable

このエラーは、検索対象のリージョンが今は利用できないことを示しています。
```

### 3-5. インラインコード

バッククォートで囲むもの：コマンド名、オプション、テーブル名、カラム名、ファイルパス、設定値、SQL キーワード（「`SELECT`文」）。

囲まないもの：製品名（TiDB、TiKV、TiUP、MySQL）。製品名は地の文で、公式の大文字小文字で書きます。

### 3-6. 図は外部作図

紙の書籍では Mermaid を使わず、PNG を `img/` に置きます。pandoc で docx に変換する工程を前提にしています。
ブログやオンラインの文書の場合はMermaid を使っても構いません。

## 4. 図表

### 4-1. 画像

```markdown
今回作成する構成は、次の図のようなものです。

![Terraform で構築する構成図](img/terraform.png)
```

- 形式は `![日本語キャプション](img/ファイル名.png)`。alt テキストがキャプションになる
- パスは章ディレクトリからの相対で `img/` を使う。`../chapterN/img/` のような自己参照は書かない
- 図番号は入れない。組版で付与される
- 図は本文で言及してから置く

### 4-2. 表

- 比較表は 1 列目のセルを太字にする
- リファレンス表は「名前／指定例／説明」の 3 列。指定例はインラインコード、説明は常体で書く

```markdown
| 型名 | 指定例 | 説明 |
| --- | --- | --- |
| INT | `INT(11)` | 4 バイトの整数型 |
```

## 5. 表記

### 5-1. 記号とスペース

- 日本語文中の括弧は全角の「（）」。半角の `()` はコードの中だけ。
- 英数字と日本語の間にスペースを入れない（「TiDBクラスター」）。
- 読点は「、」、句点は「。」。ダッシュ（`—`、`――`）と並列の中黒（・）は地の文で使わない
- プレースホルダーは `<保存先の絶対パス>` のように山括弧で書く
- コードブロックの中は、表記規約の対象外。変更しない

### 5-2. カタカナの長音

-er、-or、-ar で終わる語は長音を付けます。これは ics.media 辞書の方針で、prh が検出します。

| 長音あり | 長音なし（慣用） |
| --- | --- |
| サーバー、ユーザー、クラスター、マスター、マネージャー、リーダー、パラメーター、センター、エントリー、コンピューター | アーキテクチャ、プライマリ、リカバリ、レイテンシ、マシン |

「インターフェイス」は ics 辞書と本文の多数派に合わせ、「フェイス」と書きます。

### 5-3. ひらく漢字・閉じる漢字

prh 辞書が検出します。よく出るものだけ挙げます。

| 使う | 使わない |
| --- | --- |
| すべて | `全て` |
| さまざま | `様々` |
| たとえば | `例えば` |
| さらに | `更に` |
| したがって | `従って` |
| など | `等` |
| とおり | `通り` |
| とき | `時`（「〜するとき」の場合） |
| ため | `為` |
| ほか | `他`（ただし「その他」は漢字のまま） |
| わかる | `分かる`（「二つに分ける」は漢字のまま） |
| うえで | `上で`（位置関係を表すときは漢字のまま） |
| ごとに | `毎に` |
| 先ほど | `さきほど`、`先程` |
| 行う | `行なう` |
| 表す | `表わす` |
| 筆者たち | `筆者達` |
| アプリケーション | `アプリ` |

### 5-4. 用語の初出と併記

- 初出の用語は「日本語（English）」または「略語（Full Spelling）」で併記する。区切りは全角の「：」

```text
単一障害点（SPOF：Single Point of Failure）と呼びます。
DDL（データ定義言語：Data Definition Language）は、テーブルの構造を定義する SQL です。
```

- 初出で定義する用語は太字にする。以後は太字にせず、通称や引用は「」で示す

### 5-5. 太字と注意書き

- 太字は「用語の初出」と「箇条書きの小見出し」の 2 用途だけに使う。文中の強調には使わない
- 注意書きに専用の記法（`> **注意**`、`:::note`）は使わない。地の文に `注意点として、〜`、`〜に注意してください`、`〜ため注意が必要です` と書く
- 補足、出典 URL、前方参照は脚注 `[^名前]` にする。脚注の定義は、参照した段落の直後に空行を挟んで置き、ファイル末尾にまとめない

```markdown
TiKV の各ノードは Raft[^raft] でデータを複製します。

[^raft]: Raft の詳細は Chapter 6-3-4 で説明します。ここでは整合性を担保する仕組みとして理解してください。
```

## 6. 説明の展開

### 6-1. 基本サイクル

1 つの操作は「概念 → 実践 → 確認 → 意味づけ → 本題への接続」の順で書きます。

1. 概念：何をするか 1〜2 文で述べ、「次の SQL を実行してみてください。」で実践へ渡す
2. 実践：コードブロック
3. 確認：結果を見る操作とその出力
4. 意味づけ：出力の何に注目するか、それがなぜそうなるか
5. 本題への接続：`後ほどの章で詳しく説明しますが、分散 DB では〜に工夫が必要です` のように次へつなぐ

障害を起こして挙動を見る章は「準備（復元手段の用意）→ 壊す → エラーを見せる → 解説 → 直す」の 5 拍子です。実験の前に、必ず復元手段（バックアップ、再作成コマンド）を読者に持たせます。

### 6-2. 説明の詳しさにグラデーションを付ける

同じ操作の書き方を、章が進むにつれて簡潔にします。想定読者の外側の人が手に取っても序盤で脱落しないための仕掛けです。

| 序盤（第3章） | 後半（第5章） |
| --- | --- |
| Book テーブルを取得（SELECT）したり、挿入（INSERT）したりしてみてください。 | Book テーブルを SELECT したり、INSERT したりしてみてください。 |

### 6-3. 比喩は既知の概念に着地させる

- プログラミングの概念に例える（テーブルとクラス、行とインスタンス）
- 身近な道具に例える（表計算ソフトのシートと行）
- 和語で言い換える（正本と写本）
- 日常体験に接続する（「土日メンテナンスのため使えません」の告知）

指す内容が一意に決まらない比喩や、慣用句をひねった言い回しは使いません。

### 6-4. 割愛と行き先

範囲外を切るときは、①割愛する旨、②理由、③代わりの行き先の 3 点セットで書きます。

```text
TiProxy の詳細は本書の範囲を超えるので割愛しますが、TiDB 専用のロードバランサーだと思っていただければ大丈夫です。詳しくは公式ドキュメント[^tiproxy]を参照してください。
```

### 6-5. 構成の理由は根拠付きで

「TiKV 3 台、PD 3 台」のような構成を示すときは、なぜその数なのかを根拠（過半数の判定には奇数台が要る、など）とともに書きます。手順書ではなく理解を残す本にするためです。

### 6-6. サンプルデータは 1 セットを使い回す

最初の章で作ったサンプルデータベースを、以後の章でもそのまま使います。ダミーデータは親しみやすい造語（`りんご出版`、`ばなな書房`）で統一し、読者の認知負荷を下げます。

## 7. 運用

### 7-1. ファイル構成

対象となるプラットフォームのファイル構成に準じます。書籍に含めないメモや下書きは、ビルド対象から外れる命名（`_` 始まりなど）で区別します。

### 7-2. frontmatter

```yaml
---
author: 名前 <メールアドレス>
---
```

担当者を書く場合は `author` を使い、同じ人の表記は 1 種類に揃えます。プラットフォームが frontmatter を出力しない場合、執筆管理専用のメタデータになります。

### 7-3. textlint との付き合い方

- `.textlintrc` は `preset-ja-technical-writing` と `prh` を使う。エディターでは保存時または入力時に lint を走らせる
- 制御コメント（`<!-- textlint-disable -->`）は原則使わない。どうしても必要なときは、ルール名を指定し、最小範囲を `<!-- textlint-disable ルール名 -->` と `<!-- textlint-enable -->` で囲む
- 編集者からの表記指示は 1 か所（書籍に含めないメモファイルなど）に記録し、繰り返し出るものから prh ルールへ昇格させる。「赤入れ → 機械チェック」の昇格パスを運用の一部にする
